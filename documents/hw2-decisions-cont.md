# HW2 decisions, part 2: HW1-parity viewer features

Continues `claude/hw2-decisions.md` (same labels: **verified**, **general knowledge**, **guess**). Started Oct 15, ~17:20, because the main decisions doc is long. These features restore HW1's viewer requirements on the rebuilt app; HW2 doesn't require them, and they aren't enabled by the model.

- **HW1 version submitted: the building-footprint viewer** (Sabine, Oct 15, 17:19), tag `hw1-submission` (b8a9656). The README's HW1 sentence is correct. The other tag, `hw1-dinaa-viewer`, is the DINAA site viewer, which wasn't submitted.

- **Info strip above the viewer** (Sabine, Oct 15, ~17:00; commit `8a2b32e`). HW1 parity: HW1 §4 lists basic metadata for a viewer.
  - Id, class and split come from the `/objects` list already in memory, so they show at once. File path, vertex count and face count come from a new `GET /objects/{id}`, which loads the mesh with the same `load_mesh` as `/mesh`.
  - Why the backend computes the counts: the counts live inside the Canvas (R3F's own React root), so getting them out of three.js needs a callback across roots. The backend gives one source of truth and works even if WebGL fails. Cost: two OFF parses per click (milliseconds); no cache.
  - Fetched in an effect keyed on `selectedId` (the info exists because something is selected, which is the effect case in React's docs, general knowledge), unlike Classify, which is triggered by a click. Race guards: the `ignore` flag plus an id-tagged result; "loading" is derived (`info.id !== selectedId`), so no synchronous setState in the effect, and hooks-plugin v7 lint is clean (verified, Oct 15).
  - `source_split` is shown for val ("val (ModelNet train)"); all 599 val rows come from ModelNet's train folder (verified, manifest).
  - The strip always renders ("No object selected"), so the canvas doesn't jump on the first pick.
  - Verified Oct 15: bathtub_0001 → 1,014 vertices / 3,546 faces (matching the `/mesh` check), unknown id 404, lint clean, browser checks passed (val label, fast clicking, backend down).
- **About panel** (Sabine, Oct 15, ~17:05; commit `1d3739a`). HW1 parity: HW1 §3.3's page with the project name and a description of the data; both HW1 apps had a title plus a provenance-and-limitations paragraph (verified, both tags' `App.jsx`).
  - Shown in the right panel while nothing is selected; Classify replaces it once an object is picked. Options rejected: under the title in the sidebar (pushes the list down), a collapsed `<details>` (a first-time viewer may never open it), a header across all columns (costs viewer height).
  - No accuracy numbers in the copy: hard-coded numbers would go stale after retraining without any error. The README's Results table holds them.
  - `PredictionPanel`'s `!selectedId` branch was deleted, since App no longer renders it without a selection.
- **Label review + SQLite (section 7): decided (Sabine, Oct 15, 17:22), backend done (`d451002`).**
  - Sabine's choices: verdict ok / wrong / ambiguous with `should_be` when wrong, **plus a separate `mesh_problem` flag** (the label can be right while the mesh is broken, and the two mean different things in an analysis); **append-only history**; **`saw_prediction` recorded per review** (option b), because a verdict given after seeing "desk 91%" isn't independent of the model (automation bias, general knowledge). Options rejected for 3: ignore it (a); blind-review mode hiding probabilities until a verdict is saved (c, changes the UI flow).
  - Consequences Claude decided within those choices (flagged to Sabine): no DELETE route (a correction is a new row; cost: no return to "never reviewed"; a `withdrawn` verdict could be added later); POST, not PUT (each save adds a row); history ordered by `review_id`, not `created_at` (timestamps tie within a second, verified Oct 15: two saves shared `21:28:03`); `should_be` required iff wrong, enforced in the API (readable 422) and by a table CHECK; `should_be` equal to the current label rejected; `saw_prediction` has no default, so a forgotten field can't be recorded as "no."
  - Schema version via `PRAGMA user_version` (general knowledge: an integer in the file header): `CREATE TABLE IF NOT EXISTS` would silently keep an old table's CHECK after a verdict is added, so startup refuses any version but the current one.
  - The SQL CHECK's verdict list is built from the `Verdict` Literal, so the API and table can't drift. f-strings in SQL only ever insert our own constants; request values always go through `?` placeholders (SQL injection).
  - `sqlite3`'s connection context manager commits or rolls back but doesn't close (general knowledge), hence `db()` wraps it in try/finally.
  - "Latest per object": correlated `MAX(review_id)` subquery, served by the `(object_id, review_id)` index.
- **Review form (section 8): done (Sabine, Oct 15, 17:37–17:44; commit pending at time of writing).**
  - Sabine's choices: right column under Classify, one panel per object (draft discarded on switch); **form resets after a save**; review badges and a "Reviewed" Show filter **maybe later**.
  - `ReviewPanel` is its own component (the model's panel and the person's panel stay separate). `App` mounts it with `key={selectedId}`: a remount resets form and history with no reset effect (React's docs pattern, general knowledge). Cheap here, unlike the Canvas: plain DOM, no WebGL context.
  - History fetched inside the panel with the `ignore`-flag effect; no id tag needed because the panel is per object. After a save, the row the POST returns is prepended (it carries `review_id`, `created_at`, the stored note); alternative was a refetch (one more request; guards against other writers, none here).
  - `saw_prediction = shown?.status === 'done'`, computed in App and read at save time. Loading and error count as not seen (no probabilities on screen). `shown` is still `done` when returning to the last-classified object, and the table is visible then too, so the flag matches the screen (verified, `App.jsx`).
  - `should_be` sent only when the verdict is "wrong" (a class picked earlier stays in form state); the select excludes the current label. The Save button mirrors the backend rule (`complete`) so the gap is visible before a 422; the 422 stays the authority.
  - A one-line note under Save says how `saw_prediction` will be recorded (Claude added it, flagged as optional; it was kept).
  - Backend facts relied on (verified, `main.py`): `review_dict` returns real booleans (a `0` would render as text in JSX); `created_at` is `datetime.now(UTC).isoformat(timespec="seconds")`, so it has `+00:00` and `new Date()` shows local time correctly.
  - Verified Oct 15, ~17:44 (Sabine ran the seven checks): lint; Save disabled until complete; current class absent from the should-be list; save without Classify → no "saw prediction"; save after Classify → "saw prediction", older row below; form resets; history survives switching objects and a uvicorn restart; backend down → "Save failed… 502", form keeps its values; console clean apart from `THREE.Clock`.
- Original proposal, before Sabine's choices (kept for the record):
  - stdlib `sqlite3`, no ORM (one table, no new dependency); one connection per request (FastAPI runs plain `def` routes in a thread pool, and a sqlite3 connection by default refuses use from another thread; general knowledge).
  - One review per object, overwritten on save, with `updated_at`. Alternative: append-only history (every past verdict kept; matters for several reviewers or an audit trail; costs a "latest per object" query).
  - Fields: verdict `ok` / `wrong` / `ambiguous`; `should_be` (a class, only when wrong, checked against the class list); note.
  - Routes: `GET /reviews` (all), `PUT /objects/{id}/review` (idempotent save, unlike HW1's POST), `DELETE /objects/{id}/review`.
  - Reviews never change the manifest or training labels: a record of judgment, not a correction.
  - `.db` gitignored (user-generated state; a binary file committed from two machines conflicts). Cost: graders see reviews only in the video. Alternative: commit an exported CSV later.
